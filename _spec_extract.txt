1. 개요
1-1 목적 및 범위
본 문서는 소스코드분석 팀프로젝트 3조가 구현할 테트리스의 기능 요구사항과 모듈 간 인터페이스(API)를 하나의 문서로 정의한다. 3장 기능 명세는 시스템이 "무엇을" 제공하는지를, 4장 API 명세는 각 모듈이 "어떻게" 서로를 호출하는지를 규정하며, 두 장은 기능 ID(F-xx)로 상호 추적된다.
구현 언어는 모두 Java(17)로 한다. 게임 본체, 단위·통합 테스트, 그림 인식, 개발 보조 도구까지 전부 Java로 작성하며, 다른 프로그래밍 언어로 작성된 모듈이나 외부 프로세스를 두지 않는다. 데이터 파일(JSON, WAV)과 설정 파일(pom.xml, CI 설정)은 코드가 아니므로 이 제약의 대상이 아니다.
본 게임은 단일 PC에서 동작하는 Java 데스크톱 애플리케이션이므로, 본 문서의 API는 HTTP 엔드포인트가 아니라 패키지 경계에서 공개되는 Java 인터페이스와 클래스의 public 메서드를 의미한다. 이 결정의 근거는 2-2절에 기술한다.

1-2 용어 정의
용어
정의
미노(Mino)
낙하하는 블록. 4칸짜리는 테트로미노, 5칸짜리는 펜토미노라 한다.
SRS
Super Rotation System. 회전 시 충돌하면 정해진 오프셋(킥)을 차례로 시도해 회전을 성사시키는 표준 회전 규칙
킥(Kick) / 벽차기
SRS에서 회전 후 위치를 보정하기 위해 시도하는 좌표 이동. 벽이나 블록에 붙어 있어도 회전할 수 있게 한다.
7-Bag
7종 테트로미노를 한 주머니에 넣어 섞은 뒤 순서대로 꺼내는 무작위 생성 방식. 특정 블록의 과다·과소 출현을 막는다.
홀드(Hold)
현재 블록을 보관 슬롯에 넣고, 보관 중인 블록과 교체하는 기능
탑아웃(Top-out)
새 블록이 스폰 위치에 놓일 수 없거나 블록이 보드 위로 밀려나 게임이 끝나는 상태
세션(Session)
플레이어 1명의 보드·현재 블록·다음 블록·홀드·점수를 묶은 단위. 2인 모드에서는 세션이 2개 존재한다.
패턴(Pattern)
스테이지별 보스가 발동하는 특수 규칙(블럭 상승, 도안 매칭, 낙하 가속, 그림 인식·암전)
드로잉 턴
스테이지 5에서 블록 1개를 그려서 만들고 쌓기까지의 한 주기
경계 박스
드로잉 턴 동안 블록 대신 떨어지는 n×n(3×3 또는 4×4) 틀. 확인 전에 착지하면 벌칙 블록이 된다.
채움 비율(N%)
드로잉 패드의 한 셀에서 마우스로 칠해진 픽셀의 비율. N% 이상이면 그 셀을 그린 것으로 판정한다.
메멘토(Memento)
객체 내부 상태를 외부에 노출하지 않고 저장·복원하기 위한 스냅샷 객체
1-3 역할 분담
기능은 계층이 아닌 기능 단위(수직)로 분담한다. 공통 코어(Board, Piece, GameSession, 이벤트·입력 인터페이스)는 스프린트 0에서 3인이 함께 합의한다. 이후 코어는 역할 A가 소유하되, 보드 명세(3-5절)와 Board·BoardSnapshot·CellType 클래스는 역할 B가 소유한다. 소유자가 아닌 사람의 변경은 PR로 요청한다.

2. 시스템 구조
2-1 아키텍처 스타일 선정
아키텍처 스타일로 세 가지 후보를 비교하였다. 비교 기준은 (1) 2인용 모드 확장성, (2) 3인 병렬 개발 시 충돌 가능성, (3) 2학년 수준에서의 학습·구현 부담이다.
[표 2-1] 아키텍처 후보 비교
후보
장점
단점
판단
MVC
게임 상태(Model)와 화면(View)이 분리되어 Model 인스턴스 2개를 View 1개에 그리는 방식으로 2인용이 자연스럽게 구현된다. Swing 구조와 잘 맞는다.
Controller가 비대해지기 쉽다.
채택
계층형 (Presentation–Domain–Persistence)
계정·저장처럼 데이터 접근이 있는 기능에서 책임이 명확하다.
실시간 게임 루프와 이벤트 흐름을 표현하기 어렵다.
부분 채택 (persistence 패키지)
ECS (Entity-Component-System)
보스 패턴처럼 규칙이 많이 추가되는 게임에 유연하다.
개념 학습 부담이 크고 테트리스 규모에는 과하다.
미채택
따라서 전체 구조는 MVC를 따르되, 데이터 저장이 필요한 계정·설정·세이브 기능은 persistence 패키지에 계층형으로 분리한다. Controller의 비대화는 입력을 Command 패턴으로, 게임 진행 단계를 State 패턴으로 분리하여 완화한다.
2-2 주요 설계 결정
각 결정마다 두 개 이상의 대안을 비교하고 선택 근거를 남긴다(ADR 방식).

선택
근거
구현 언어
① Java 단일
② Java + Python(그림 인식 등 일부)
①
팀 합의 사항이다. 언어가 하나이면 IntelliJ 하나로 전체 소스를 분석·리팩터링·정적분석할 수 있어 강의 목표와 맞고, 프로세스 간 통신이나 두 번째 실행 환경을 배포할 필요가 없다.
빌드 도구
① Gradle(Groovy/Kotlin DSL 스크립트)
② Maven(pom.xml 선언형 설정)
②
Gradle 빌드 파일은 Groovy·Kotlin 코드이므로 Java 단일 언어 원칙과 어긋난다. Maven은 선언형 XML 설정만으로 빌드되고 IntelliJ가 기본 지원한다.
API 형태
① REST(HTTP) 서버 API
② 프로세스 내 Java 인터페이스
②
3조 기능에는 네트워크 기능이 없다. 서버를 두면 배포·예외 처리 부담만 늘고 이점이 없다. Java 인터페이스는 컴파일 시점에 계약 위반을 잡아 준다.
게임 루프
① 별도 스레드 + sleep
② javax.swing.Timer
②
Timer 콜백은 이벤트 디스패치 스레드(EDT)에서 실행되므로 화면 갱신과 게임 로직 간 동기화 문제가 생기지 않는다.
분담 방식
① 계층별(Model/View/Data)
② 기능별 수직 분담
②
한 기능이 여러 계층에 걸쳐 있어 ①은 상호 대기가 잦다. ②는 feature 브랜치 단위로 병렬 개발과 기여 추적이 가능하다.
모듈 간 통지
① 직접 메서드 호출
② Observer(이벤트 버스)
②
줄 삭제 한 번에 보스 HP, 효과음, 연출이 동시에 반응해야 한다. 코어가 사운드·보스 코드를 알 필요가 없어 결합도가 낮아진다.
저장 포맷
① Java Serializable
② JSON(Gson)
②
클래스 구조가 바뀌어도 필드 단위로 호환성을 유지하기 쉽고, 사람이 읽을 수 있어 디버깅이 쉽다. 역직렬화 취약점 위험도 없다.
비밀번호 저장
① SHA-256 단순 해시
② BCrypt(외부 라이브러리)
③ PBKDF2(JDK 내장)
③
①은 무차별 대입에 약하다. ③은 반복 해시와 솔트로 충분히 안전하며 외부 의존성 없이 JDK만으로 구현된다.
화면 전환
① 화면마다 새 창
② GameState에 통합
③ CardLayout + 중앙 라우터
③
전환 규칙·접근 제한·뒤로 가기 이력이 한 곳에 모이고 화면끼리 서로를 몰라도 된다. 상세 비교는 2-5절 [표 2-4]
라우트 파라미터
① Map<String, Object>
② 라우트별 record
②
키 오타·타입 오류를 컴파일 시점에 잡는다. 라우트가 받는 값이 코드에 문서처럼 드러난다.
그림 인식 방식
① 딥러닝(CNN) 분류
② 셀 채움 비율(N%) 판정 + 규칙 기반 도형 검사
②
딥러닝은 사실상 Python 도구에 의존하므로 Java 단일 언어 원칙과 어긋나고, 학습 데이터 수집 부담도 크다. ②는 패드를 n×n 셀로 나눠 칠해진 비율로 셀을 판정하고 연결성·템플릿을 검사하는 방식이라 순수 Java로 구현되며, 판정 기준(N%)을 숫자로 조정할 수 있다. ShapeRecognizer 인터페이스로 분리해 두었으므로 필요하면 Java 기반 학습 라이브러리 구현체로 교체할 수 있다.
2-3 패키지 구조와 의존성 규칙
kr.jbnu.tetris
 ├─ app          Main, GameWindow                         (공통)
 ├─ core         Piece, PieceType, Cell, GameSession,
 │                GameEngine, ScoreCalculator             (A)
 │                Board, BoardSnapshot, CellType          (B)
 ├─ piece        PieceFactory, Randomizer, SevenBagRandomizer,
 │                RotationSystem, SrsRotationSystem, HoldSlot (A)
 ├─ input        Action, Command, KeyBindings, InputHandler (B)
 ├─ event        GameEvent, GameEventType, GameEventBus    (공통)
 ├─ stage        Boss, StageManager, BossPattern 및 구현체  (C)
 ├─ state        GameState 및 구현체                       (C)
 ├─ recognition  ShapeRecognizer, TemplateShapeRecognizer  (C)
 ├─ persistence  AccountService, SaveService, Settings...  (A·B)
 ├─ audio        SoundManager                              (C)
 ├─ ui.router    Route, RouteParams, Screen, ScreenRouter,
 │                RouteGuard 및 구현체                      (A)
 └─ view         GamePanel, BoardView, 각 Screen·Overlay   (각 기능 담당)
의존성은 다음 규칙을 따른다. 규칙 위반은 코드 리뷰(PR)에서 반려한다.
core와 piece는 event 외의 어떤 패키지에도 의존하지 않는다. 즉 코어는 화면·사운드·저장을 모른다.
view는 Model을 읽기만 하며, 상태 변경은 input(Command) 또는 GameEngine을 통해서만 한다.
audio, stage, view의 이펙트는 GameEventBus 구독으로 동작하며 코어 클래스를 직접 수정하지 않는다.
persistence는 core의 메멘토 타입에만 의존하고, core는 persistence를 모른다.
화면(Screen)끼리는 서로를 참조하지 않으며, 화면 이동은 반드시 ScreenRouter를 통한다. core는 ui.router를 모른다.

펜토미노·사용자 그림 블록 등 종류가 늘어도 PieceFactory에 생성 규칙만 추가하면 된다. Prototype은 복제할 원형 관리가 오히려 번거롭다.
무작위 생성 (A)
Strategy / 조건 분기
Strategy
Randomizer 인터페이스 뒤에서 7-Bag과 순수 랜덤, 펜토미노 삽입 정책을 교체할 수 있고 시드 고정 테스트가 쉽다.
회전 (A)
하드코딩 분기 / 데이터 기반 테이블
테이블
SRS 킥 오프셋을 표(KickTable)로 두면 I 전용·펜토미노용 테이블 추가가 코드 수정 없이 가능하다.
입력·2인용 (B)
직접 if-else / Command
Command
키 코드 → (플레이어, 동작) 매핑을 Map으로 관리하므로 2인 키 분리와 키 설정 저장이 같은 구조로 해결된다.
보스 패턴 (C)
Strategy / Template Method
Strategy
스테이지별 패턴은 공통 흐름이 거의 없는 서로 다른 알고리즘이므로 교체형인 Strategy가 적합하다.
게임 진행 (C)
enum+switch / State
State
준비·진행·일시정지·드로잉·클리어·게임오버마다 허용 입력이 달라 switch가 비대해진다. 상태별 클래스로 전이 규칙을 분리한다.
화면 전환 (A)
개별 창 / Mediator(중앙 라우터)
Mediator
화면 N개가 서로 직접 이동하면 연결이 N×N으로 늘어난다. 라우터를 거치면 각 화면은 라우터 하나만 알면 된다. 접근 규칙은 RouteGuard(Strategy)로 분리한다.
통지 (공통)
직접 호출 / Observer
Observer
2-2절 [표 2-2] 참조
저장 (A)
직접 직렬화 / Memento + Repository
Memento + Repository
세션(A)과 스테이지(C)가 각자 스냅샷을 제공하고 파일 입출력은 Repository 뒤에 숨긴다. 담당자 간 코드 침범이 없다.
2-5 화면 구조 및 라우팅
게임 외 화면(타이틀, 로그인, 모드 선택, 결과 등)의 전환은 중앙 라우터(ScreenRouter)가 담당한다. 화면마다 라우트 ID와 경로 문자열을 부여하여 기능 명세(3장), 라우터 API(4-12절), 테스트가 같은 이름으로 화면을 가리키도록 한다. 이는 체크리스트 3-5(UI/UX 설계, 화면 흐름)의 산출물을 겸한다.
화면 전환 방식으로 다음 세 가지를 비교하였다.

3-2 기본 게임플레이 및 블록 시스템 (역할 A)
F-00 기본 게임플레이
기능 ID / 이름
F-00  기본 게임플레이
담당 / 우선순위 / 점수
A (공통 코어, 보드 규칙은 B) / Must / - (전제 기능)
설명
폭 10칸, 가시 높이 20칸(숨김 스폰 영역 4행 별도, 규격은 3-5절)의 보드에서 블록을 이동·회전·낙하시키고, 가로 한 줄이 가득 차면 삭제하는 기본 규칙이다. 원본 소스코드에 이미 구현된 부분은 분석 후 재사용하고, 3조 기능이 요구하는 구조(세션 분리, 이벤트 발행)로 리팩터링한다.
입력
좌/우 이동, 소프트 드롭(↓), 하드 드롭, 회전, 일시정지 키
처리 흐름
중력 주기마다 블록을 1칸 아래로 이동한다.
아래로 이동할 수 없으면 블록을 보드에 고정(lock)하고 PIECE_LOCKED 이벤트를 발행한다.
가득 찬 줄을 찾아 삭제하고 LINES_CLEARED 이벤트를 발행한다.
다음 블록을 스폰한다. 스폰 위치가 막혀 있으면 탑아웃으로 게임오버한다.
출력 / 결과
점수: 1줄 100, 2줄 300, 3줄 500, 4줄 800점에 현재 스테이지 번호를 곱한다. 소프트 드롭 1칸당 1점, 하드 드롭 1칸당 2점.
예외 처리
일시정지 중에는 모든 이동 입력을 무시한다.
인수 조건
AC-00-1 블록이 보드 밖이나 다른 블록과 겹치는 위치로 이동하지 않는다.
AC-00-2 가득 찬 줄이 여러 개면 한 번에 삭제되고 위 블록이 그만큼 내려온다.
AC-00-3 스폰 위치가 막히면 GAME_OVER 이벤트가 1회 발행된다.
관련 API
Board, Piece, GameSession, GameEngine, ScoreCalculator (4-2절)
F-01 SRS (Super Rotation System)
기능 ID / 이름
F-01  SRS (Super Rotation System)
담당 / 우선순위 / 점수
A / Must / 0.5
설명
회전 결과가 벽이나 블록과 충돌하면 SRS 킥 테이블의 오프셋을 순서대로 시도하여 처음으로 충돌하지 않는 위치에 블록을 배치한다(벽차기). 시계·반시계 회전을 모두 지원한다.
선행 조건
활성 블록이 존재하고 게임 상태가 PLAYING이다.
입력
시계 방향 회전 키, 반시계 방향 회전 키
처리 흐름
현재 회전 상태(0, R, 2, L)와 방향으로 목표 회전 상태를 계산한다.
블록 종류의 킥 그룹(JLSTZ 공용 / I 전용 / O 없음)으로 킥 테이블을 조회한다.
테스트 1(오프셋 0,0)부터 테스트 5까지 순서대로 canPlace를 검사한다.
처음 성공한 위치로 블록을 교체하고 PIECE_ROTATED 이벤트를 발행한다.
출력 / 결과
회전된 블록. 모든 테스트가 실패하면 블록은 변하지 않는다.
인수 조건
AC-01-1 왼쪽 벽에 붙은 T 블록을 회전하면 오른쪽으로 밀려 회전된다.
AC-01-2 I 블록은 I 전용 킥 테이블을 사용한다.
AC-01-3 O 블록은 회전해도 칸 위치가 변하지 않는다.
AC-01-4 5개 테스트가 모두 실패하면 블록의 위치·회전 상태가 그대로이다.
관련 API
RotationSystem, SrsRotationSystem, KickTable (4-3절)
F-02 다음 블록 미리보기 및 7-Bag 생성
기능 ID / 이름
F-02  다음 블록 미리보기 및 7-Bag 생성
담당 / 우선순위 / 점수
A / Must / 1
설명
7종 테트로미노를 한 주머니에 넣고 섞은 뒤 차례로 꺼내며, 주머니가 비면 새로 채운다. 앞으로 등장할 블록 5개를 미리보기 영역에 표시한다.
처리 흐름
주머니를 Fisher–Yates 방식(시드 고정 Random)으로 섞는다.
대기열 길이가 미리보기 개수보다 짧아지면 새 주머니를 뒤에 붙인다.
블록이 스폰될 때마다 미리보기를 갱신한다.
출력 / 결과
미리보기 영역에 다음 블록 5개가 순서대로 표시된다.
인수 조건
AC-02-1 주머니 경계 기준 연속 7개 블록에 같은 종류가 중복되지 않는다.
AC-02-2 같은 종류 블록 사이의 간격은 최대 12개를 넘지 않는다(펜토미노 미삽입 기준).
AC-02-3 미리보기 첫 번째 블록이 실제로 다음에 스폰되는 블록과 같다.
AC-02-4 같은 시드로 생성하면 같은 순서가 나온다(테스트·세이브 복원용).
관련 API
Randomizer, SevenBagRandomizer, PentominoPolicy (4-3절)
F-03 블록 홀드(Hold)
기능 ID / 이름
F-03  블록 홀드(Hold)
담당 / 우선순위 / 점수
A / Must / 0.5
설명
현재 블록을 홀드 슬롯에 보관하고, 이미 보관된 블록이 있으면 교체하여 꺼낸다.
입력
홀드 키
처리 흐름
슬롯이 비어 있으면 현재 블록을 보관하고 대기열에서 다음 블록을 스폰한다.
슬롯에 블록이 있으면 서로 교체하고, 꺼낸 블록은 스폰 위치·기본 회전 상태로 시작한다.
한 블록당 1회만 허용하며, 블록이 고정되면 다시 허용한다.
스테이지 5(드로잉 턴)에서는 홀드를 사용하지 않는다.
출력 / 결과
홀드 영역에 보관 블록이 표시된다. 사용 불가 상태에서는 흐리게 표시한다.
인수 조건
AC-03-1 같은 블록으로 연속 두 번 홀드할 수 없다.
AC-03-2 꺼낸 블록은 항상 스폰 방향(회전 상태 0)이다.
AC-03-3 홀드로 스폰한 블록이 막히면 탑아웃 처리된다.
관련 API
HoldSlot, GameSession.hold() (4-2, 4-3절)

AC-04-2 펜토미노도 이동·회전·줄 삭제·홀드 규칙이 동일하게 적용된다.
AC-04-3 펜토미노가 삽입되어도 테트로미노 7종은 주머니마다 1개씩 등장한다.

F-06 게임 진행 상황 저장 및 이어하기
기능 ID / 이름
F-06  게임 진행 상황 저장 및 이어하기
담당 / 우선순위 / 점수
A / Should / 1
설명
진행 중인 게임의 현재 스테이지, 보스 체력, 보드 상태 등을 파일로 저장하고, 나중에 불러와 이어서 플레이한다. 로그인 사용자마다 슬롯 3개를 제공한다.
선행 조건
로그인 상태이며 게임 상태가 PAUSED이다. 비로그인 상태로 저장·이어하기 화면(SAVE_SLOTS)에 들어가면 AuthGuard가 로그인 화면으로 안내한다.
입력
일시정지 메뉴의 [저장] 또는 타이틀 화면의 [이어하기], 슬롯 번호(1~3)
처리 흐름
저장: GameEngine이 각 세션과 StageManager에서 메멘토를 모아 GameMemento를 만들고 SaveService에 넘긴다.
SaveService는 임시 파일에 쓴 뒤 원자적으로 교체하여 저장 중 종료되어도 기존 파일이 손상되지 않게 한다.
불러오기: 파일을 읽어 버전을 확인하고 GameEngine.restoreFrom으로 복원한 뒤 PAUSED 상태로 시작한다.
출력 / 결과
저장 항목: 모드, 스테이지, 보스 HP, 경과 시간, 세션별 보드·현재 블록·대기열·7-Bag 상태·홀드·점수·삭제 줄 수, 보스 패턴 진행 상태(스테이지 5는 턴 번호, 그리는 사람, 잠금 셀 마스크 포함)
예외 처리
게스트는 저장할 수 없으며 로그인을 안내한다. 줄 삭제 연출 중에는 저장 메뉴를 비활성화한다. 스테이지 5 드로잉 턴 중에 저장하면 진행 중인 박스와 그림은 저장하지 않으며, 불러오면 그 턴을 스폰 위치부터 다시 시작한다. 파일 손상이나 버전 불일치 시 오류 메시지를 표시하고 해당 슬롯을 "손상됨"으로 표시한다.
인수 조건
AC-06-1 저장 후 불러오면 보드, 현재/다음/홀드 블록, 보스 HP, 스테이지가 저장 시점과 같다.
AC-06-2 불러온 뒤 등장하는 블록 순서가 저장하지 않고 계속 진행했을 때와 같다.
AC-06-3 손상된 파일을 불러와도 프로그램이 종료되지 않는다.
관련 API
SaveService, GameMemento, SessionMemento, GameEngine.createMemento/restoreFrom, 라우트 SAVE_SLOTS·PAUSE·AuthGuard (4-2, 4-9, 4-12절)

F-07 단일 PC 2인용 협동 모드
기능 ID / 이름
F-07  단일 PC 2인용 협동 모드
담당 / 우선순위 / 점수
B / Must / 5
설명
하나의 화면에 두 플레이어의 보드를 좌우로 배치하고, 한 키보드에서 키 입력을 분리하여 실시간으로 함께 플레이한다. 두 플레이어는 같은 보스를 공유하며, 각자 지운 줄의 데미지가 공동 보스 HP를 깎는다(기본안, 6-2절 Q1).
선행 조건
모드 선택 화면(MODE_SELECT)에서 [2인 협동]을 선택하면 참여 확인 화면(COOP_LOBBY)으로 이동한다. P1·P2는 각각 로그인 또는 게스트로 참여한다.
입력
P1 키 세트와 P2 키 세트(3-6절 기본 키 배치), 공통 일시정지 키
처리 흐름
GameEngine이 GameSession 2개를 만든다. 각 세션은 독립된 보드, 7-Bag(서로 다른 시드), 홀드를 가진다.
InputHandler는 키 코드로 (플레이어, 동작)을 조회하여 해당 세션에만 Command를 실행한다.
좌우 이동 키를 누르고 있을 때의 자동 반복(DAS 170ms, ARR 50ms)은 플레이어별로 독립 계산한다.
어느 세션에서든 LINES_CLEARED가 발생하면 StageManager가 공동 보스에 데미지를 준다.
두 플레이어 중 한 명이라도 탑아웃하면 게임오버한다(기본안, 6-2절 Q2).
예외(스테이지 5): 보드를 공유 보드 1개로 전환하고, 한 명이 그리고 한 명이 쌓는 역할 분담 방식으로 진행한다(F-14).
출력 / 결과
좌우 보드, 플레이어별 미리보기·홀드·점수, 화면 상단 공동 보스 HP 바
예외 처리
키보드 동시 입력 한계(고스팅)를 줄이기 위해 기본 키 배치를 양손 영역으로 분리한다.
인수 조건
AC-07-1 두 플레이어가 동시에 키를 눌러도 서로의 블록에 영향이 없다.
AC-07-2 P1과 P2가 각각 2줄씩 지우면 보스 HP가 2줄 데미지의 두 배만큼 줄어든다.
AC-07-3 한 명이 탑아웃하면 양쪽 모두 게임오버 화면이 표시되고 각자의 기록이 저장된다.
AC-07-4 1인 모드와 2인 모드가 같은 GameSession 클래스를 사용한다.
AC-07-5 스테이지 5에 진입하면 보드가 1개로 바뀌고 쌓는 사람의 키만 동작한다.
관련 API
GameEngine.start(COOP_LOCAL), InputHandler, KeyBindings, Command, 라우트 MODE_SELECT·COOP_LOBBY·GAME (4-2, 4-4, 4-12절)
F-08 환경설정 (키 입력 설정 및 저장)
기능 ID / 이름
F-08  환경설정 (키 입력 설정 및 저장)
담당 / 우선순위 / 점수
B / Should / 0.5
설명
환경설정 화면에서 1인 모드, 2인 모드 P1·P2의 동작별 키를 직접 눌러서 지정하고, [저장]을 눌러 파일에 저장한다. 타이틀 화면과 일시정지 메뉴 양쪽에서 들어갈 수 있다.
입력
탭(1인 / 2인 P1 / 2인 P2) 선택 → 동작 선택 → 새 키 입력(키 캡처), [기본값 복원], [저장], [닫기]
처리 흐름
동작을 선택하면 "새 키를 누르세요" 상태가 되고, 다음에 눌린 키를 캡처한다.
이미 다른 동작이나 다른 플레이어에 쓰이는 키면 변경을 거부하고 어느 동작과 겹치는지 안내한다.
변경 사항은 화면 안에서만 임시로 유지되며 [저장]을 눌러야 파일에 기록되고 게임에 적용된다.
저장 시 로그인 사용자는 사용자별 파일에, 게스트는 공용 파일에 기록한다.
저장하지 않은 변경이 있는 상태로 [닫기]를 누르면 "저장 / 버리기 / 취소" 확인 창을 띄운다(Screen.canLeave).
일시정지 메뉴에서 저장한 설정은 게임으로 돌아가는 즉시 적용된다.
예외 처리
Esc 키는 키 캡처 취소용으로 예약되어 할당할 수 없다. 파일 저장에 실패하면 기존 설정을 유지하고 오류를 안내한다.
인수 조건
AC-08-1 중복 키 지정 시 변경되지 않고 안내 문구가 표시된다.
AC-08-2 [저장] 후 프로그램을 재시작해도 변경한 키가 유지된다.
AC-08-3 저장하지 않고 [버리기]로 닫으면 이전 키 설정이 그대로이다.
AC-08-4 [기본값 복원] 후 저장하면 3-6절의 기본 키 배치와 같아진다.
AC-08-5 일시정지 메뉴에서 키를 바꿔 저장하면 게임 재개 후 새 키로 조작된다.
관련 API
KeyBindings, SettingsRepository, 라우트 SETTINGS (4-4, 4-9, 4-12절)

회원가입, 로그인, 로그아웃을 제공하고 사용자별 최고 기록과 플레이 데이터를 관리한다.

사용자별 기록: 최고 점수, 최고 도달 스테이지, 플레이 횟수, 누적 삭제 줄 수. 기록 화면(RECORDS)에서 조회한다.

로그인 실패 시 아이디와 비밀번호 중 어느 쪽이 틀렸는지 구분하지 않고 같은 문구를 표시한다. 비밀번호는 평문으로 저장·로그 출력하지 않는다.
인수 조건
AC-09-1 이미 존재하는 아이디로 가입할 수 없다.
AC-09-2 users.json 파일에 비밀번호 평문이 존재하지 않는다.
AC-09-3 최고 점수보다 높은 점수로 게임을 마치면 최고 점수가 갱신된다.
AC-09-4 게스트의 플레이 기록은 저장되지 않는다.
관련 API
AccountService, UserRepository, PasswordHasher, 라우트 LOGIN·SIGNUP·RECORDS (4-9, 4-12절)

F-10 보스전 시스템 및 체력 관리
기능 ID / 이름
F-10  보스전 시스템 및 체력 관리
담당 / 우선순위 / 점수
C / Must / 1
설명
스테이지 1~5마다 보스가 등장하고, 줄을 삭제하면 보스 HP가 줄어든다. 보스를 처치하면 다음 스테이지로 이동하며, 스테이지 5 보스를 처치하면 게임 클리어이다.
처리 흐름
LINES_CLEARED 이벤트를 받으면 데미지 표(1줄 10, 2줄 25, 3줄 40, 4줄 60)에 따라 보스 HP를 줄이고 BOSS_DAMAGED를 발행한다.
피격 시 HP 바를 흔들고 피격음을 재생한다.
HP가 0이 되면 BOSS_DEFEATED를 발행하고 STAGE_CLEAR 상태로 전이한다. 2초 연출 후 보드를 비우고 다음 스테이지를 시작한다.
보스 최대 HP 초기값: 스테이지 1=100, 2=150, 4=200, 5=250. 스테이지 3은 도안 완성으로 격파한다(F-12).
출력 / 결과
화면 상단 보스 이름·HP 바. 스테이지 3에서는 HP 대신 도안 완성률을 표시한다.
인수 조건
AC-10-1 4줄을 한 번에 지우면 보스 HP가 60 감소한다.
AC-10-2 HP는 0 미만으로 내려가지 않는다.
AC-10-3 스테이지 5 보스 처치 시 GAME_CLEAR가 발행된다.
관련 API
Boss, StageManager, DamageTable (4-6절)

일정 시간마다 쌓인 블록 전체가 위로 1칸 상승하고, 맨 아래에 구멍 1칸이 있는 방해 줄이 추가된다.

F-14 스테이지 5 보스 패턴: 그림 인식 AI 및 암전
기능 ID / 이름
F-14  스테이지 5 보스 패턴: 그림 인식 AI 및 암전
담당 / 우선순위 / 점수
C / Could / 미표기 (6-2절 Q4)
설명
최종 보스 스테이지에서는 모든 블록을 플레이어가 마우스로 직접 그려서 만든다. 블록 대신 n×n 경계 박스(n은 3 또는 4)가 보드 위에서 떨어지는 동안 드로잉 패드에 색칠하면, 인식기가 패드를 n×n 셀로 나누어 각 셀의 N% 이상이 칠해졌으면 그 셀을 그린 것으로 판단한다. 인식된 도형이 경계 박스를 대신해 블록이 된다. 박스가 바닥에 닿을 때까지 그리지 못하면 n×n 격자가 꽉 찬 벌칙 블록으로 바뀐다. 제안서의 2초 암전 패턴도 함께 동작한다.
선행 조건
스테이지 5 시작. 2인 모드에서는 스테이지 5 진입 시 좌우 보드 2개를 공유 보드 1개로 전환한다.
입력
마우스 좌클릭 드래그(칠하기), 우클릭 드래그(지우기), 패드의 [확인] 버튼, 쌓는 사람의 좌우 이동 키
처리 흐름
드로잉 턴 시작: 스폰 위치에 n×n 경계 박스가 나타나 드로잉 전용 속도(기본 1행/700ms)로 떨어진다. 박스는 활성 블록처럼 충돌 판정을 받으며 좌우 이동만 가능하다(회전·소프트/하드 드롭·홀드 불가).
칠하기: 드로잉 패드(셀당 64px, 붓 반지름 10px)에 마우스로 자유롭게 칠한다.
셀 판정: 각 셀의 칠해진 픽셀 비율이 N(기본 50%) 이상이면 그 셀을 그린 것으로 본다.
확인: [확인]을 누르면 인식기가 도형을 판정한다. 유효하면 칠한 셀 위치 그대로 경계 박스 자리에 CUSTOM 블록으로 교체되고, 이후 일반 블록처럼 회전·드롭이 가능하다. 무효하면 사유를 표시하고 박스는 계속 떨어진다.
실패: 확인 전에 박스가 더 내려갈 수 없게 되면 그 위치에 n×n 벌칙 블록(PENALTY)으로 고정된다.
블록이 고정되면 다음 드로잉 턴이 시작된다. 스테이지 5에서는 7-Bag, 미리보기, 홀드를 사용하지 않는다.
2인 모드: 공유 보드 1개를 한 명만 조작한다. 블록마다 역할을 교대하며(첫 턴은 P1이 그리고 P2가 쌓음), 쌓는 사람은 자기 키 세트로 조작하고 그리는 사람은 마우스를 쓴다. 직전 턴에 인식된 블록이 차지했던 패드 셀은 잠금 처리되어 칠할 수 없다(직전 도형과 겹치지 않게 막음).
1인 모드: 한 사람이 마우스로 그리고 키보드로 박스와 블록을 조작한다. 잠금 규칙은 적용하지 않는다(6-2절 Q11).
암전: 25초 주기로 2초간 보드 영역(경계 박스·블록 포함)을 가린다. 드로잉 패드는 가리지 않는다.
출력 / 결과
패드에 셀별 채움 비율 표시(기준 이상 셀은 테두리 강조), 인식 결과 문구(예: "T 미노로 인식", "사용자 도형", "연결되지 않음: 다시 그리세요", "시간 초과: 벌칙 블록")
예외 처리
인식 유효 조건: 그린 셀이 1개 이상이고, 모든 그린 셀이 상하좌우로 연결되어 있을 것. 잠금 셀은 칠해지지 않으므로 판정에서 항상 제외된다. 직전 턴이 벌칙 블록이었거나 스테이지 첫 턴이면 잠금 셀이 없다. 일시정지 중에는 박스가 멈추고 패드 입력도 막힌다.
인수 조건

내용
배치 가능
블록의 모든 칸이 0 ≤ x < 10, 0 ≤ y < 24 범위 안이고 해당 칸이 EMPTY일 때만 배치할 수 있다.

줄 판정
숨김 영역을 포함한 모든 행이 대상이다. 한 행의 10칸이 모두 EMPTY가 아니면 가득 찬 줄이다.
줄 삭제
가득 찬 줄을 동시에 지우고, 그 위의 행들을 지운 줄 수만큼 아래로 내린다. 떠 있는 블록이 추가로 떨어지는 연쇄 중력은 적용하지 않는다.
방해 줄 상승
모든 행을 한 칸 위로 올리고 23행에 구멍 1칸이 있는 GARBAGE 줄을 넣는다(F-11). 0행에 블록이 있었다면 보드 밖으로 밀려나므로 탑아웃이다.
탑아웃 ① Block out
새 블록을 스폰 위치에 배치할 수 없다.
탑아웃 ② Lock out
블록이 고정될 때 그 블록의 모든 칸이 숨김 영역(0~3행)에 있다.
탑아웃 ③ Push out
방해 줄 상승으로 블록이 0행 밖으로 밀려난다.
도안 영역
스테이지 3 도안(F-12)은 가시 영역 하단 6행(18~23행)에 겹쳐 그린다. 도안 판정은 이 영역만 대상이다.

스테이지 5(F-14)의 n×n 박스는 활성 블록과 같은 충돌 판정을 받는다. 확인 전에 더 내려갈 수 없게 되면 박스의 모든 칸이 PENALTY로 고정된다. 확인되면 박스 안의 그린 셀만 CUSTOM 블록이 된다.

4. API 명세
4-1 공통 규약
모든 공개 API는 다음 규약을 따른다. 원본 소스코드 분석 결과 규약과 다른 부분이 있으면 원본에 맞추어 본 절을 개정한다.
항목
규약
구현 언어
모든 API는 Java 17로 정의·구현한다. 본 장의 시그니처는 Java 문법(record, sealed interface, Optional 등)을 그대로 따른다.
좌표계
보드 폭 10, 전체 높이 24(상단 0~3행은 숨김 스폰 영역). x는 0(왼쪽)~9, y는 0(맨 위)~23(맨 아래)이다. 상세 규격은 3-5절.
불변 객체
Piece, Cell, GameEvent 및 모든 메멘토는 불변(record)이다. 이동·회전은 새 객체를 반환한다.
스레드
게임 로직과 이벤트 발행은 모두 Swing EDT에서 실행한다. 다른 스레드에서 호출하지 않는다.
시간 단위
모든 시간 값은 밀리초(long)이다.
플레이어 번호
playerIndex 0 = 1인 모드 플레이어 또는 P1, 1 = P2
예외
잘못된 인자는 IllegalArgumentException, 잘못된 호출 시점은 IllegalStateException, 사용자 입력·파일 오류는 checked 예외(4-13절)로 알린다.
null
공개 메서드는 null을 반환하지 않는다. 값이 없을 수 있으면 Optional을 반환한다.

// CoverageShapeRecognizer 처리 절차
1. 셀 판정: coverage[r][c] >= threshold 이고 잠금 셀이 아니면 그린 셀
2. 그린 셀이 0개 → INVALID(EMPTY)
3. BFS로 상하좌우 연결성 검사 → 끊어져 있으면 INVALID(DISCONNECTED)
4. 라벨링용으로만 경계 상자를 잘라 (0,0) 기준 정규화
5. 테트로미노·펜토미노 템플릿과 4회전 × 좌우대칭 비교 → 일치 라벨 또는 "CUSTOM"
6. 블록 생성에는 정규화 전 좌표(cellsInBox)를 사용 → 칠한 위치 그대로 블록이 됨
